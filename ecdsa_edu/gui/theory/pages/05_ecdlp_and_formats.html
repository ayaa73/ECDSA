5 · Why Q hides d, and how keys are written down

The elliptic-curve discrete-logarithm problem (ECDLP)

Everyone knows the curve, G and your public key Q = d · G. The problem "given G and Q, find d" is called the elliptic-curve discrete-logarithm problem. The security of ECDSA rests on it being too hard to solve.

On a toy curve it is easy

On toy-17 there are only 18 possible private keys, so an attacker simply lists all multiples of G = (5, 1) and looks for Q:

kk·Gkk·Gkk·G
1(5, 1)7(0, 6)13(16, 4)
2(6, 3)8(13, 7)14(9, 1)
3(10, 6)9(7, 6)15(3, 16)
4(3, 1)10(7, 11)16(10, 11)
5(9, 16)11(13, 10)17(6, 14)
6(16, 13)12(0, 11)18(5, 16)

If Q = (0, 6), the table says d = 7. (And 19 · G = O, so the list repeats after that.)

On a real curve it is hopeless

The points k·G jump around the curve with no visible pattern, so there is nothing better to do than to search. The best known general method (Pollard's rho) needs about √n steps:

CurveSize of nWork to find dComment
toy-175 bitsa handful of stepsby hand
secp256k1, P-256256 bitsabout 2128 stepsfar beyond all computers on Earth

Compare the two directions on a 256-bit curve: computing Q from d takes a few hundred point operations; computing d from Q takes about 2128. That gap is the "one-way street" that makes public-key signatures possible.

Note. Nobody has proved that the ECDLP is hard; it is an assumption that has survived decades of research. A large quantum computer running Shor's algorithm would break it.

Writing a public key down: SEC 1 encoding

A point has two coordinates. The standard way to turn it into bytes puts one marker byte in front and writes each coordinate with a fixed length (as many bytes as p needs):

FormBytesMeaning
Uncompressed04 | X | Yboth coordinates
Compressed02 | XX only, and Y is even
Compressed03 | XX only, and Y is odd

Why compression works

For a given x, the curve equation y² = x³ + ax + b (mod p) has at most two solutions: y and p − y. Because p is odd, one of them is even and the other is odd. So X plus one bit ("even or odd?") is enough to rebuild the whole point - the key is half as long.

Example

Q = (0, 6) on toy-17 (coordinates fit in one byte):

  • Uncompressed: 04 00 06
  • Compressed: 02 00  (6 is even)

Decompressing 02 00: x = 0 gives y² = 0³ + 2·0 + 2 = 2 (mod 17). The square roots of 2 modulo 17 are 6 and 11 (6² = 36 = 2 mod 17). The marker 02 asks for the even one, so y = 6.

On secp256k1 a compressed public key is 33 bytes (66 hex digits) and an uncompressed one is 65 bytes (130 hex digits).

Key files in ECDSA Lab

The Keys page saves keys as small, readable text files in JSON format. All numbers are written in hexadecimal:

FileContent (d = 7 on toy-17)
Private key{"curve": "toy-17", "d": "0x7"}
Public key{"curve": "toy-17", "Qx": "0x0", "Qy": "0x6"}

For a custom curve the file also stores the curve itself (p, a, b, Gx, Gy, n, h), so the key can be loaded on another computer.

  • When a file is loaded, everything in it is checked again: the curve, the range of d, and the four public-key checks from page 4.
  • A file cannot redefine a built-in curve: if it says "secp256k1" and brings its own numbers, they must match exactly.
  • Private key files are not encrypted. Real software protects them with a password or keeps keys in secure hardware. This program is for learning only.

Good habits with keys

  • Never share, e-mail or screenshot a private key.
  • Generate keys with a cryptographic random generator, never by hand.
  • Always validate a public key you receive before using it.
  • Use standard curves with at least 256 bits for anything real.
