How a key pair is generated

NameWhat it isWho knows itUsed for
Private key da whole number, 1 ≤ d ≤ n − 1only the ownercreating signatures
Public key Qa point on the curve, Q = d · Geverybodychecking signatures
  1. Pick d at random from 1, 2, …, n − 1. Every value must be equally likely.
  2. Compute Q = d · G with double-and-add (see step 1).
  3. Keep d secret. Publish Q.

There is no "encryption" step: the public key is just the result of a multiplication on the curve.

Why d must be truly random

  • If an attacker can guess d, they own the key. A d taken from a weak generator (a timestamp, random.random(), a small number) can be guessed quickly.
  • If d is biased (some values more likely than others), the search becomes easier.

ECDSA Lab therefore takes d from the operating system's cryptographic random generator (Python's secrets module): d = secrets.randbelow(n − 1) + 1. randbelow gives a uniform number in 0 … n − 2, and adding 1 moves it to 1 … n − 1.

Why 0 and n are not allowed

  • d = 0 would give Q = O (the point at infinity), which is not a usable public key.
  • d = n gives the same result, because n · G = O. In general d and d + n produce the same Q, so only 1 … n − 1 are different keys.

Checking a public key you receive

A public key from somebody else is untrusted input. Before using it, check that:

  1. Q is not the point at infinity;
  2. both coordinates are in the range 0 … p − 1;
  3. Q satisfies the curve equation y² = x³ + ax + b (mod p);
  4. n · Q = O, i.e. Q is one of the multiples of G.

Skipping these checks allows "invalid-curve" tricks, where an attacker sends a point from a different, weaker curve. ECDSA Lab runs all four checks whenever a public key is pasted or loaded.

Why Q hides d: the ECDLP

Everyone knows the curve, G and your public key Q = d · G. The problem "given G and Q, find d" is the elliptic-curve discrete-logarithm problem (ECDLP). The security of ECDSA rests on it being too hard to solve.

On a toy curve it is easy

On toy-17 there are only 18 possible private keys, so an attacker simply lists all multiples of G (the table in step 1) and looks for Q. If Q = (0, 6), the list says d = 7.

On a real curve it is hopeless

The points k·G jump around the curve with no visible pattern, so there is nothing better to do than to search. The best known general method (Pollard's rho) needs about √n steps:

CurveSize of nWork to find dComment
toy-175 bitsa handful of stepsby hand
secp256k1, P-256256 bitsabout 2128 stepsfar beyond all computers on Earth

Computing Q from d takes a few hundred point operations; computing d from Q takes about 2128. That gap is the "one-way street" that makes public-key signatures possible.

Note. Nobody has proved that the ECDLP is hard; it is an assumption that has survived decades of research. A large quantum computer running Shor's algorithm would break it.

Writing a public key down: SEC 1 encoding

The standard way to turn a point into bytes puts one marker byte in front and writes each coordinate with a fixed length (as many bytes as p needs):

FormBytesMeaning
Uncompressed04 | X | Yboth coordinates
Compressed02 | XX only, and Y is even
Compressed03 | XX only, and Y is odd

Why compression works

For a given x, the curve equation has at most two solutions: y and p − y. Because p is odd, one of them is even and the other is odd. So X plus one bit ("even or odd?") is enough to rebuild the whole point, and the key is half as long.

Example: Q = (0, 6) on toy-17 is 04 00 06 uncompressed and 02 00 compressed (6 is even). Decompressing 02 00: x = 0 gives y² = 2 (mod 17), whose square roots are 6 and 11 (6² = 36 = 2 mod 17). The marker 02 asks for the even one, so y = 6.

On secp256k1 a compressed public key is 33 bytes (66 hex digits) and an uncompressed one is 65 bytes (130 hex digits).

Keeping keys safe

  • ECDSA Lab can save your public key as a small JSON file (or a certificate) so others can check your signatures. For a custom curve the file also stores the curve itself, and everything in it is checked again when it is loaded.
  • Your private key is never saved by the app. Copy it and keep it in a safe place such as a password manager; real software also protects keys with a password or keeps them in secure hardware.
  • Never share, e-mail or screenshot a private key.
  • Generate keys with a cryptographic random generator, never by hand.
  • Use standard curves with at least 256 bits for anything real.
